## 1. AI가 하는 일은 세 가지

StoryZip의 AI는 복잡해 보이지만, 하는 일은 세 가지뿐입니다.

| # | 기능 | 언제 실행? | 누가 트리거? | 한 줄 설명 |
|---|------|-----------|-------------|-----------|
| 1 | **회차 인덱싱 (+ 설정집 자동 추출)** | 자동 저장 이벤트 발생 시 | 시스템 (자동 저장 5초 → 디바운스 5초 후 실행) | 회차를 쪼개고 요약해서 AI 재료창고에 넣고, 얕은 인물·용어·복선 후보를 `extraction_suggestion`에 적재 |
| 2 | **초안 생성** | 작가가 버튼 누를 때 | 작가 (수동) | 재료창고에서 관련 정보를 꺼내 다음 화 초안 작성 |
| 3 | **검수 (맞춤법 포함)** | 작가가 버튼 누를 때 | 작가 (수동) | 원고가 기존 설정과 모순되는지 + 고유명사 기반 맞춤법 체크 |

세 기능 모두 본질은 같습니다:
**"DB에서 관련 재료를 꺼내서 → 프롬프트로 조립해서 → LLM에 보내고 → 응답을 저장하거나 보여준다"**

> **설정집 자동 추출**은 ① 인덱싱에 통합된 부가 기능입니다. 임포트 전용 "풀 프로필 자동 생성"은 MVP에서 제외하고, 임포트 시에도 일반 저장과 동일한 ① 흐름을 회차 수만큼 반복한 뒤 작가가 검토 UI에서 병합·보완합니다.

## 2. 데이터가 흘러가는 큰 그림

```
작가가 회차를 저장한다 (즉시 "저장됨" 표시)
        │
        │ (마지막 저장 후 5초 디바운스 — 연속 저장 시 타이머 리셋)
        ▼
┌─────────────────────────────────────────┐
│  ① 회차 인덱싱 (자동, 백그라운드)            │
│                                          │
│  원문 → 플레인 텍스트 변환                   │
│       ├→ 500~1,000 토큰씩 쪼개기 → 임베딩  │
│       │   → 벡터 저장 (episode_chunk)     │
│       └→ LLM 요약 → 요약 + 인물·용어·떡밥  │
│           후보 저장 (episode_summary,      │
│                     extraction_suggestion) │
└─────────────────────────────────────────┘
        │
        ▼  (재료창고가 채워진 상태)
        │
        ├─── 작가가 "초안 생성" 클릭 ──────────┐
        │                                    ▼
        │    ┌──────────────────────────────────┐
        │    │  ② 초안 생성 (SSE 스트리밍)        │
        │    │                                  │
        │    │  재료창고에서 8가지 꺼내기:         │
        │    │  작품정보 + 설정집 + 최근요약 +    │
        │    │  관련과거요약(벡터) + 직전원문 +   │
        │    │  복선 + 스토리라인                 │
        │    │       ↓                           │
        │    │  하나의 프롬프트로 조립             │
        │    │       ↓                           │
        │    │  Claude Sonnet에 전달 (stream)     │
        │    │       ↓                           │
        │    │  초안을 실시간 스트리밍 표시         │
        │    └──────────────────────────────────┘
        │
        └─── 작가가 "검수" 클릭 ─────────────┐
                                            ▼
             ┌──────────────────────────────────┐
             │  ③ 검수                            │
             │                                   │
             │  재료창고에서 꺼내기:                │
             │  이번 원고 + 설정집 + 작품정보 +    │
             │  관련 요약 + 복선                  │
             │       ↓                           │
             │  하나의 프롬프트로 조립             │
             │       ↓                           │
             │  Claude Sonnet에 전달 (JSON)       │
             │       ↓                           │
             │  충돌 목록 → 작가에게 표시           │
             └──────────────────────────────────┘
```

임포트 시에는 위 ① 흐름을 회차 수만큼 반복한 뒤, 매 회차가 쌓아둔 `extraction_suggestion` 항목을 작가 검토 UI에서 병합·승인합니다. 상세는 [ai-data-pipeline.md §3](ai-data-pipeline.md)을 참고하세요.

## 3. "재료창고"란 무엇인가

AI가 잘 답하려면 작품에 대한 정보가 필요합니다. 이 정보가 저장되는 곳을 "재료창고"라고 부릅니다.
재료창고는 특별한 게 아니라 **DB 테이블 여러 개**입니다.

### 재료의 종류

| 재료 | 어디에 저장? | 누가 채우나 | 언제 쓰이나 |
|------|-------------|-----------|-----------|
| **작품 메타데이터** (시대, 장르, 톤, 문체) | `plan` | 작가 직접 | 초안 생성, 검수 |
| **회차 원문** | `episode` | 작가 직접 | 인덱싱 입력, 초안 생성 (말투 샘플) |
| **회차 조각 + 벡터** | `episode_chunk` | 인덱싱이 자동 | 초안 생성, 검수 (벡터 검색) |
| **회차 요약** | `episode_summary` | 인덱싱이 자동 → 작가 승인 | 초안 생성, 검수 (맥락 파악) |
| **등장인물 설정** | `character` + `character_custom_field` | 작가 직접 (+ AI 추천) | 초안 생성, 검수 |
| **인물 임베딩** | `character_embedding` | 인덱싱이 자동 | 벡터 검색 |
| **세계관 설정·용어** | `world_note` | 작가 직접 (+ AI 추천) | 초안 생성, 검수 |
| **세계관 임베딩** | `world_note_embedding` | 인덱싱이 자동 | 벡터 검색 |
| **복선** | `foreshadow` + `foreshadow_link` | 작가 직접 (+ AI 추천) | 초안 생성, 검수 |
| **추출 제안 큐** | `extraction_suggestion` | AI가 자동 추출 | 작가 승인 UI |

> **핵심 원리**: 작가가 쓸수록 재료창고가 풍성해지고, 재료가 풍성할수록 AI 품질이 올라갑니다.
>
> **용어 테이블 주의**: 별도 `dictionary` 테이블은 **폐기**되었습니다. 용어도 세계관의 일부로 보고 `world_note`에 통합 관리합니다.

## 4. 기능별 상세: 인풋과 아웃풋

### 4.1 회차 인덱싱

> 작가가 회차를 저장하면 **마지막 저장 후 5초 뒤**에 자동으로 돌아가는 백그라운드 작업.
> 작가는 기다릴 필요 없이 다른 작업을 하면 됩니다.

**5초 디바운스 이유**: 작가가 타이핑 중 에디터가 자주 자동저장 이벤트를 발생시키는 경우, 매번 인덱싱하면 임베딩 API 비용이 폭발합니다. 마지막 저장 후 5초간 추가 저장이 없으면 "한 문단 완료"로 간주해 한 번만 실행합니다.

**인풋**

```
episode.content (TipTap JSON)
    ↓ extractPlainText()
플레인 텍스트 (태그 제거, 순수 글자만)
```

**처리 과정**

```
플레인 텍스트
    ├→ [청킹] 500~1,000 토큰 단위로 쪼개기 (단락 경계 우선, tiktoken)
    │       ↓
    │   각 조각을 임베딩 API에 전송 (배치)
    │       ↓
    │   조각 원문 + 벡터 → episode_chunk 테이블 UPSERT
    │
    └→ [요약] 회차 전문을 LLM(Claude Haiku)에 전송
            ↓
        "이 회차를 요약하고, 등장인물/신규 용어/떡밥 후보를 추출해줘"
            ↓
        JSON 파싱
            ├→ 요약 + 인물 목록 → episode_summary UPSERT
            └→ 신규 용어/인물/떡밥 후보 → extraction_suggestion INSERT
                                          (status='pending')
```

**아웃풋**

| 저장 위치 | 내용 | 용도 |
|----------|------|------|
| `episode_chunk` | 조각 원문 + 벡터 (회차당 약 10개) | 나중에 "비슷한 장면 찾기" |
| `episode_summary` | 요약 3~5문장 + 등장인물 + 떡밥 후보 | 나중에 "맥락 파악" |
| `extraction_suggestion` | 신규 용어/인물/떡밥 추천 (작가 승인 대기) | 작가 승인 UI |

**사용 모델**
- 임베딩: OpenAI `text-embedding-3-small` (1536차원)
- 요약: Claude Haiku 4.5

**비용**: 1화당 약 15~30원

### 4.2 초안 생성

> 작가가 "다음 화 초안 생성" 버튼을 누르면 실행.
> 작가가 스토리라인을 입력하면 AI가 그에 맞는 초안을 SSE로 실시간 스트리밍해줍니다.

**인풋 (작가가 직접 입력하는 것)**

```
- 이번 화에서 벌어질 사건 (자유 텍스트, 1~5문장)
- 강조할 캐릭터
- 포함/회수할 떡밥 (기존 목록에서 선택)
- 목표 분량 (글자수)
- 톤 조정 (긴장감, 감성, 유머 등)
```

**인풋 (서버가 DB에서 자동으로 꺼내는 것)**

```
┌─────────────────────────────────────────────────┐
│  프롬프트 조립 (RAG 컨텍스트, 최대 ~28K 토큰)      │
│                                                  │
│  1. 시스템 프롬프트                                │
│     "작가의 말투·톤·설정을 따르는 어시스턴트"        │
│                                                  │
│  2. 작품 메타데이터 ← plan                         │
│     시대, 장르, 톤, 문체 (약 500 토큰)              │
│                                                  │
│  3. 관련 설정집                                    │
│     ← character + character_custom_field          │
│     ← world_note (용어 포함)                       │
│     이름 매칭 + character_embedding /              │
│     world_note_embedding 벡터 유사도 검색          │
│     (약 2,000~5,000 토큰)                         │
│                                                  │
│  4. 관련 떡밥 ← foreshadow + foreshadow_link       │
│     작가 선택 + 미회수 떡밥 중 관련 있는 것          │
│     (약 500~1,000 토큰)                           │
│                                                  │
│  5. 최근 5~10화 요약 ← episode_summary             │
│     (is_approved=true 우선) (약 2,000~4,000 토큰)  │
│                                                  │
│  6. 관련 과거 요약 ← episode_summary + 벡터 검색    │
│     스토리라인과 의미적으로 비슷한 과거 화 3~5개      │
│     (약 1,500~3,000 토큰)                         │
│                                                  │
│  7. 직전 1~2화 원문 ← episode                      │
│     말투 참고용 (약 10,000~15,000 토큰)            │
│                                                  │
│  8. 작가 스토리라인 (작가 입력)                     │
│     (약 500~1,000 토큰)                           │
│                                                  │
│  총: 약 17,000~30,000 토큰                        │
└─────────────────────────────────────────────────┘
```

**처리 과정**

```
조립된 프롬프트
    ↓
Claude Sonnet에 1회 스트리밍 호출 (temperature=0.8)
    ↓
SSE로 프론트에 실시간 전달 (첫 청크 ≤ 2초)
    ↓
작가 에디터에 실시간 표시 — 원하면 "이어 쓰기"로 연장
```

**아웃풋**

```
- SSE 스트림: data: {"draftIndex":0, "content":"..."} ... data: [DONE]
- 작가가 채택하면 에디터에 삽입
- 작가가 수정 후 저장하면 → 인덱싱 파이프라인(4.1)이 자동 실행
```

> 초안 다중 생성(2~3개 병렬)은 비용 2~3배 → **기본은 SSE 1개 + 이어 쓰기 옵션**. 다중 생성은 유료 플랜 기능으로 검토.

**사용 모델**: Claude Sonnet 4.5
**비용**: 1회 생성 약 180~270원

### 4.3 검수

> 작가가 "이 회차 검수" 버튼을 누르면 실행.
> 원고가 기존 설정과 모순되는 부분을 찾아줍니다.

**인풋 (서버가 DB에서 자동으로 꺼내는 것)**

```
┌─────────────────────────────────────────────────┐
│  프롬프트 조립 (약 15K 토큰)                        │
│                                                  │
│  1. 검수 대상 원고 ← episode                       │
│  2. 작품 메타데이터 ← plan                         │
│  3. 관련 설정집 ← character + world_note           │
│     (이름 매칭 + 벡터 검색)                          │
│  4. 관련 떡밥 ← foreshadow + foreshadow_link       │
│  5. 관련 과거 요약 ← episode_summary (벡터 검색)    │
└─────────────────────────────────────────────────┘
```

**아웃풋 (JSON)**

```json
{
  "conflicts": [
    {
      "type": "setting_conflict",
      "severity": "high",
      "location": "3번째 문단",
      "issue": "박서진이 검을 왼손에 쥐고 있는데, 설정에는 오른손잡이로 되어 있음",
      "reference": "character: 박서진 → 오른손잡이",
      "suggestion": "왼손 → 오른손으로 수정, 또는 설정을 양손잡이로 변경"
    },
    {
      "type": "tone_conflict",
      "severity": "medium",
      "location": "7번째 문단",
      "issue": "'OK'라는 표현이 조선시대 배경에 부적합",
      "reference": "plan: 시대 → 조선 후기",
      "suggestion": "'좋소' 또는 '그리하시오'로 변경"
    }
  ],
  "newItems": [
    {
      "type": "character",
      "name": "마을 이장 김씨",
      "description": "5번째 문단에서 등장, 설정집에 없음 → 추가 제안"
    }
  ]
}
```

**사용 모델**: Claude Sonnet 4.5
**비용**: 1회 검수 약 90원

## 5. 담당별 역할 경계

이 시스템을 만들려면 **두 사람이 각각 뭘 하는지** 명확해야 합니다.

### 백엔드/파이프라인 담당이 만드는 것 (Spring Boot)

```
1. TipTap JSON → 플레인 텍스트 변환기 (extractPlainText)
   - episode.content에서 순수 텍스트를 뽑는 함수
   - AI 쪽에서 "이 함수 호출하면 텍스트 나옴"이라고 믿고 쓸 수 있어야 함

2. 저장 이벤트 디바운서 (5초)
   - episode_id별 타이머 관리 (in-memory Map 또는 Redis)
   - 5초 후 FastAPI /v1/pipelines/episode 호출

3. ai_job CRUD + 프로그레스 API
   - 작업 생성/상태 변경/조회
   - 프론트가 폴링할 진행률 조회 API

4. DB에서 재료 꺼내는 API
   - Plan, Character, WorldNote, Foreshadow 조회
   - 최근 N화 요약, 벡터 유사도 상위 K개 청크 등

5. 토큰 차감/환불 + 감사 로그
   - AI 호출 전 잔액 확인, 호출 후 차감
   - 실패 시 환불 + token_transaction 기록

6. 결과 저장 (FastAPI → Spring 내부 API)
   - episode_chunk, episode_summary, extraction_suggestion INSERT
   - ai_analysis INSERT

7. 임포트 파서 (파일 → 회차 분리 → episode INSERT)
```

### AI 담당이 만드는 것 (FastAPI + Celery)

```
1. Celery + Redis 셋업 (docker, worker)
   - 큐: draft(고), review(고), indexing(중)
   - 재시도 정책 데코레이터

2. 청킹 로직
   - 플레인 텍스트 → 500~1,000 토큰 조각
   - 단락 경계 우선, tiktoken 측정

3. 임베딩 호출 (배치)
   - OpenAI text-embedding-3-small
   - Rate limit 대응

4. 프롬프트 설계
   - 인덱싱용 (요약 + 인물/용어/떡밥 추출)
   - 초안 생성용
   - 검수용
   - ai_prompt_template 테이블로 버전 관리

5. RAG 컨텍스트 조립 로직
   - Spring API로 재료 조회
   - 벡터 검색 + 키워드 매칭 조합
   - 토큰 예산(28K) 내 우선순위 채움

6. LLM 호출 + 응답 파싱
   - Claude/OpenAI API 호출 (LangChain)
   - JSON 응답 Pydantic 검증, 실패 시 보정 재요청 1회
   - SSE 스트리밍 (초안 생성)

7. 품질 평가
   - 더미 데이터 테스트셋
   - 프롬프트 튜닝
```

### 접점 (둘이 합의해야 하는 것)

```
- AI Input Contract: AI에 넘기는 데이터의 정확한 형태
- AI Output Contract: AI가 돌려주는 데이터의 정확한 형태
- 에러 처리: LLM 실패 시 재시도 정책, 토큰 환불 여부
- 비용 관리: 기능별 토큰 소비량, 사용자 토큰 차감량
- 디바운스 정책: 5초 확정, 향후 조정 시 양측 합의
```

## 6. 임포트 vs 일반 저장

|   | 임포트 (100화 일괄) | 일반 저장 (1화씩) |
|---|-------------------|------------------|
| **언제** | 최초 1회 | 매번 저장할 때 |
| **입력** | 파일 업로드 (.txt, .docx, .md) | 에디터에서 저장 |
| **전처리** | 회차 자동 분리 필요 | 이미 회차 단위 |
| **디바운스** | 없음 (일괄 트리거) | **5초** |
| **인덱싱** | N개 큐에 한 번에 → 수십 분 | 1개 큐에 → 수 초 |
| **UX** | 프로그레스 바 + "AI가 읽는 중" | 백그라운드, 작가 모름 |
| **이후** | 매 회차가 쌓아둔 `extraction_suggestion` → 검토 UI에서 일괄 승인 | 요약 카드 1장 표시 |
| **인덱싱 자체** | 동일한 파이프라인 | 동일한 파이프라인 |

> **결론**: 임포트는 "큰 작업을 회차 수만큼 반복"이고, 이후는 완전히 같은 흐름입니다. 임포트 전용 풀 프로필 자동 생성 단계는 두지 않습니다.

## 7. 핵심 용어 사전

팀 내에서 같은 단어를 같은 뜻으로 쓰기 위한 정리입니다.

| 용어 | 뜻 |
|------|-----|
| **인덱싱** | 회차 원문을 AI가 활용할 수 있는 형태(조각+벡터, 요약)로 가공하는 과정 |
| **청킹** | 긴 텍스트를 500~1,000 토큰 조각으로 나누는 것 |
| **임베딩** | 텍스트를 숫자 벡터(1536차원)로 변환. 의미 유사한 텍스트는 벡터도 가까움 |
| **벡터 검색** | 임베딩 벡터 간 거리를 계산해 "의미적으로 비슷한 것"을 찾는 검색 |
| **RAG** | Retrieval-Augmented Generation. DB에서 검색(R) → 프롬프트 증강(A) → LLM 생성(G) |
| **컨텍스트 조립** | LLM에 보낼 프롬프트를 만들기 위해 여러 테이블에서 재료를 꺼내 합치는 과정 |
| **프롬프트** | LLM에 보내는 전체 입력 텍스트 (시스템 지시 + 재료 + 작가 요청) |
| **토큰** | LLM의 처리 단위. 한글 1글자 ≈ 1~2토큰. 비용과 직결 |
| **재료창고** | AI가 참조하는 모든 DB 데이터 총칭 (설정집 + 요약 + 벡터 + 메타데이터) |
| **pgvector** | PostgreSQL에서 벡터를 저장·검색할 수 있게 해주는 확장 |
| **TipTap JSON** | 에디터(TipTap)가 저장하는 서식 포함 문서 형식. AI 입력 전 플레인 텍스트 변환 필요 |
| **플레인 텍스트** | 서식 태그가 모두 제거된 순수 글자 |
| **디바운스** | 연속된 이벤트 중 마지막 하나만 처리하는 기법. 타이핑 중 자동저장 이벤트 중복 방지 |
| **Celery** | Python 비동기 작업 큐 라이브러리. Redis를 브로커로 사용 |
| **SSE** | Server-Sent Events. 서버→클라 단방향 실시간 스트림. 초안 생성에 사용 |
| **PowerSync** | 서버 Postgres ↔ 클라 SQLite 양방향 동기화 미들웨어. 벡터 테이블은 제외 |
